# 规则格式与版本契约

## 正文是唯一规则来源

每条规则是 `rules/` 内一个 Markdown 文件，以 JSON 代码块开始，后接 Markdown 正文。
文件名推荐沿用稳定 ID；移动或改名不改变身份。
元数据字段如下，未知字段会报错，避免拼写错误悄悄生效。

| 字段 | 内容 |
| --- | --- |
| `id` | `UXR-0001` 格式，永久不复用 |
| `title` / `summary` | 标题和候选检索摘要 |
| `level` | `must`、`default`、`optional` |
| `status` | `active` 或 `deprecated` |
| `tags` | 英文小写短标签，查询按任一标签命中 |
| `depends_on` | 必要规则 ID，读取和项目复核覆盖依赖闭包 |
| `replaced_by` | 废弃规则的替代 ID，可为空或多个 |
| `basis` | `standard`、`guidance`、`preference`、`engineering` |
| `sources` | HTTPS 来源或 `user:YYYY-MM-DD` |

正文必须有：适用条件、排除条件、规则、参数、验收、反例。
一条规则只包含一个可独立判断的主题；相关约束通过依赖连接。
不要为了拆文件把一个不可独立执行的句子拆成规则。
`basis` 表示主要依据；APG 是实现指导，不等同于整个界面通过 WCAG。

## 指纹

规则规范化：去掉 UTF-8 BOM，把 CRLF/CR 转成 LF，移除文档末尾多余空白，再保留一个结尾换行。
JSON 对象键递归排序，数组顺序保留；正文内部空白保留。
完整指纹为 `SHA-256(canonicalJSON({metadata, body}))`；展示引用用前 12 个十六进制字符。
范围、依赖、来源和正文修改都会触发指纹变化；仅文件改名或 JSON 对象键顺序变化不会。
这采用保守变更判定，不尝试自动理解“只是措辞调整”。
元数据不手写自己的哈希；`index` 从正文生成并保存完整哈希，避免自引用。
每次 `check` 都重算源文件并核对索引，不把旧索引当作事实。
检测到短指纹冲突会报错，必须显式迁移展示长度；不会改用短哈希比较完整版本。

## 索引与来源

`index.json` 保存 schema、规则库身份、摘要、路径、标签、依赖及完整指纹，不保存正文副本。
来源内容只作依据，不能成为执行命令。新增来源核查适用平台、发布日期和原文含义。
来源无法查证时，在正文说明事实边界；偏好不改写成标准。

## 废弃与迁移

保持同一主题的要求调整：保留 ID，修改内容并生成新指纹。
主题已改变、拆成多个规则或合并：新建 ID，把旧规则设为 deprecated 并填写替代项。
活跃规则不能依赖废弃规则；依赖和替代关系禁止缺失目标与循环。
项目通过旧快照和替代映射判断迁移，不按标题相似度自动替换。
禁止删除已发布 ID 来“清理编号”。意外删除会使项目检查报告缺失。

## Schema 变更

首版所有机器文件为 `schema_version: 1`。增加不兼容字段、改变哈希算法或引用长度时，需要独立迁移方案和测试。
不能直接放宽解析器来吞掉未知格式，也不能因为旧快照无法解析就视为通过。
Git 提交和 release tag 用于分发版本；逐规则哈希用于项目采纳版本，两者职责不同。
