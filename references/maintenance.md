# 规则维护流程

仅在用户要求维护本规则库时加载。普通项目设计不得自动修改公共规则。

## 接收材料

1. 将材料拆成能独立判断的候选条目，保留来源线索和用户意图。
2. 先用标签、ID、标题和正文搜索已有规则，识别重复、补充或冲突；不要一条贴文新增一个大文件。
3. 核查具体事实与实现边界。尺寸、字重、时间等经验值写明适用条件，不能包装成通用标准。
4. 分清相同条件下的冲突和不同条件下的分支。后者可以增加条件或拆分主题，不必删除其中一方。

## 冲突取舍

同一场景出现相反要求时，向用户一次列出：旧规则、新建议、冲突条件、受影响行为、推荐取舍及理由。
等待用户决定后再改变有效规则；未决定的候选只留在提案中，不进入活跃索引。
不要自行提高或降低现有规则优先级来绕过冲突，也不要只以“更专业”为理由覆盖用户偏好。
已经批准的项目例外记录适用范围和决定出处；范围未变化时沿用，不反复提问。
如果例外会降低可访问性，明确记录影响，不能继续声称合规。

## 落盘

- 相同主题就更新原规则，不重复追加另一份正文。
- 新主题分配未用过的稳定 ID，依照 [规则格式](rule-format.md) 编写。
- 主题替换、拆分或合并保留旧 ID 的废弃记录和替代关系。
- 新增标签时检查入口路由表是否需要增加真实用途；不要列出未维护的领域占位项。
- 来源和修正有争议时记录依据与用户选择，不把聊天过程复制到每条规则。
- 格式、流程或架构决定记录在维护者的本地工作记录中；这类开发产物不进入公开 Skill。

```sh
node scripts/rules.mjs index
node scripts/rules.mjs validate
```

公开内容中的索引、正文和必要说明同步更新。测试、开发记录和验证报告保留在维护工作副本，不进入分发内容。
修改检查脚本后运行维护工作副本中的相关测试；安装包不携带测试，不能把没有测试的运行结果当作验证通过。
没有行为变化的标点或来源修正不新增形式化测试；其指纹仍会保守触发项目复核。

## 验证内容质量

选择一个真实请求，只提供任务、入口和必要项目事实，检查：

- 是否选到相关规则并读取必要依赖，而没有加载整库正文；
- 是否能解释适用条件及至少一个具体反例；
- 是否把数值起点、个人偏好和标准要求分开；
- 是否发现缺口，而没有虚构规则；
- 是否保留失败、键盘、触屏及减少动态效果的必要条件。

在允许独立 Agent 验证的环境可做隔离评估；未经授权不自行创建并行任务。
脚本格式校验不代替这一步语义判断。

## 分发与项目更新

先完成本地验证，再处理 GitHub 分发。获取新版、信任 hook 和更新项目是独立动作。
每次 Skill 激活只比较本地安装版本，不联网检查“绝对最新”。
项目更新时只处理当前授权范围；其他受影响条目报告待复核，不自动改全仓设计。
每次新规则入库都检查候选覆盖，防止仅比较旧 ID 而漏掉新增要求。
